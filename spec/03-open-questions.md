| Q54 | JS budget (08, Q22: ≤150 KB gzip first load on Plans) vs. measured baseline: empty Next 16 static-export page (W-01) = 174,176 B ≈ 170 KB gzip (gzip -9 sum of the 6 JS chunks referenced by `out/index.html`; `next build` no longer prints First Load JS; webpack gives about the same). | Q55 | Root redirect (08 Routes, Q14): `en` exists in every market (`ee/en`, `lt/en`, `lv/en`). Which market does a visitor with only `en` get? | Q56 | A 2xx body that fails the Zod schema (API drift), or a 2xx with non-JSON body. Not in 05. | Frontend | Client throws an `ApiError` `{status: <http status>, code: 'invalid_response', kind: 'server'}`; callers treat it like 5xx. Logging is not specified yet (no W-item owns it). Also: an unlisted 4xx status (e.g. 402, 403) gets code `request_failed` (05 lists none) and kind `badRequest`. |
| Q57 | 05 says fetch "times out" → network, but no timeout value exists. How is a caller abort classified? | Frontend | Every request gets `AbortSignal.timeout(15 s)`, combined with an optional caller `signal` on `getPlans`, `getMe` and `getOrder`. `createOrder` deliberately takes none: aborting a POST leaves it unknown whether the order was created (Q34). Timeout → `{status: 0, code: 'network', kind: 'network'}`. Caller abort → `{status: 0, code: 'aborted', kind: 'network'}`; callers ignore it (no UI, no retry). An abort or timeout while the body is read is classed the same as one during fetch. |
| Q58 | 04 doesn't say what a reload does on CreatingOrder or Gate (transient, no page of their own), nor what Polling does with `badRequest` or other unlisted error kinds. | Product | `begin` (on-enter re-run) is a no-op on CreatingOrder and Gate, so a reload never creates an order (inv. 1; Gate step 2 is post-slice). Polling and Unconfirmed keep their state on any error kind not listed in 04, never PaymentFailed (inv. 3). |
| Q59 | 04 says Pay is disabled after a Gate step 1 5xx/network "until the check succeeds" but names no event that re-runs the check. | Product | Retry point shows a "Check again" action while Pay is disabled: it re-runs step 1 for display only (`retryCheck`), never continues to an order. `failed`/404 clears the open order and re-enables Pay, `pending` → Resume, `paid` → Confirmed. A reload or bfcache restore (`begin`) clears the disabled flag and the consent error; the notice stays (inv. 6); the Gate on Pay still catches an open order (inv. 1). |
| Q60 | 04 lists PaymentFailed as a state but its on-enter is "go to the retry point with notice". | Product | PaymentFailed = transition into the retry point with a `payment_*` notice (04 on-enter); no resting state. |
