## Alerts whose signal the app doesn't emit

- **Alert 6 (client errors)**: nothing emits it. 04, 07 and 08 define no error tracker. 07 bans error messages in GA and cut the error events, and Q49 is still open. If nobody adds a tracker, this alert has no data.
- **Alert 3 (API 5xx)**: only sees errors that reach the server. Network, CORS (Q40) and timeout failures that 04 routes to StartError, VerifyError or "Connection issue" are invisible. The app emits nothing for those.
- **Alert 7 (synthetic)**: a static callback page always returns 200 from the CDN. The check proves the HTML exists, not that the return works. It's a probe signal; the app adds nothing to it.
- **Alert 8**: `purchase` exists, but analytics is out of the slice (PLAN), so it's only valid in prod. Its baseline moves with the consent rate.
- **Alerts 1, 2, 4, 5**: backend signals, which is fine. But 05's backend requests don't ask for these metrics or dashboards, so there is no owner commitment.

## A user on the payment page during each rollback

The provider page itself is never affected. Each case below is about what happens when the user comes back.

1. **Bad deploy, restore**: OK if the "additive for two releases" rule holds. Nothing enforces it: there's no test in 09. A user who returned during the bad window keeps the open order and is resumed at the Gate.
2. **`checkout.paused`, provider down**: this one **strands users**.
   - Pause blocks StartingEid. The only exit from IdentityLost ("Verify") and from OtherBrowser ("Start again here") goes through StartingEid.
   - So a user whose session expired, or who returns in another browser, can't see their order status. This contradicts the principle that "IdentityLost ignores every kill switch".
   - Also, "Continue payment" during pause sends the user back to a provider that is down.
3. **Wrong price**: the pause doesn't stop a payment already in flight, so the user pays the wrong amount. Only "Backend refunds" covers it, with no message to the user. Also has the IdentityLost gap from item 2.
4. **`offShare` = 0**: the doc contradicts itself. "Arm is fixed per flow" (stored or `rs` wins) versus "next show re-derives: off-arm flows get Review". There's no forced-override rule.
   - The retry point after a failed payment is undefined: Plans in the off arm (Q38), Review in the on arm.
5. **LV pause or rebuild**:
   - Pause: the IdentityLost and OtherBrowser gap again.
   - Rebuild with `market.LV` off:
     - Callbacks check locale with `resolvePair`, which now rejects LV. They fall back to `/ee/et/`, so an LV user returning from payment sees Estonian.
     - A failed payment redirects to `/`, then into EE pages. Stored context still says LV but the URL says EE, so the user risks an order in the wrong market or with the wrong VAT.
6. **Bad CMS publish**: the claim "callbacks don't read CMS copy" is wrong. Confirmed shows the plan title, which comes from CMS `title` (06). A bad publish that passes validation shows wrong copy on return until it's reverted.
7. **Duplicate orders**: same as item 1. The user is not paused, so a double charge is still possible until the fix ships.
8. **Config fetch down**: the Gate falls back to defaults, so an off-arm user flips to on mid-flow. Whether that's allowed depends on the unresolved item 4 contradiction. Kill switches are silently off, and the only fallback is a rebuild, which takes minutes.
